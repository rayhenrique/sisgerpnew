# Correção da Restauração de Backups

## Problema Identificado

**Erro 1**: `invalid input syntax for type bigint: "00000000-0000-0000-0000-000000000000"`  
**Erro 2**: `invalid input syntax for type uuid: "0"`  
**Erro 3**: `Não é possível excluir: a categoria está vinculada a receitas/despesas`

**Causas**:
1. O sistema tem tabelas com diferentes tipos de `id` (UUID vs bigint)
2. Existem **restrições de integridade referencial** (foreign keys) entre tabelas
3. Tabelas devem ser deletadas na ordem correta para respeitar as foreign keys

## Estrutura de Dependências

```
expenses → categories (foreign key)
expenses → expense_classifications (foreign key)
revenues → categories (foreign key)
audit_logs → profiles (foreign key)
categories → categories (self-reference via parent_id)
```

**Ordem correta de deleção**:
1. **Primeiro**: Tabelas dependentes (expenses, revenues, audit_logs)
2. **Segundo**: Tabelas referenciadas (expense_classifications, categories)
3. **Último**: Tabelas independentes (profiles)

## Solução Aplicada

**Arquivo**: `src/server/backup/services/restoreService.ts`

Implementei **duas melhorias críticas**:

### 1. Detecção Automática do Tipo de ID

```typescript
// Define which tables use UUID vs bigint
const uuidTables = new Set([
  'profiles',
  'report_schedules',
  'report_jobs',
]);

// Determine id type: check explicit list first, then inspect data
let isUuid = uuidTables.has(tableName);

// If not in explicit list and has data, try to detect from data
if (!isUuid && tableData.rows.length > 0) {
  const firstRow = tableData.rows[0];
  const idValue = firstRow.id;
  isUuid = typeof idValue === 'string' && idValue.includes('-');
}

// Use appropriate delete condition
if (isUuid) {
  deleteQuery = deleteQuery.neq('id', '00000000-0000-0000-0000-000000000000');
} else {
  deleteQuery = deleteQuery.gte('id', 0);
}
```

**Vantagens**:
- ✅ Lista explícita para tabelas conhecidas (funciona mesmo se vazias)
- ✅ Detecção automática para tabelas desconhecidas (se tiverem dados)
- ✅ Fallback seguro para bigint

### 2. Ordem Correta de Deleção (Foreign Keys)

```typescript
// Define deletion order to respect foreign key constraints
const deletionOrder = [
  // First: Tables that reference others (dependent tables)
  'expenses',           // References categories, expense_classifications
  'revenues',           // References categories
  'report_schedules',   // May reference other tables
  'report_jobs',        // May reference other tables
  'audit_logs',         // References profiles
  
  // Second: Tables that are referenced by others (parent tables)
  'expense_classifications',  // Referenced by expenses
  'categories',              // Referenced by revenues, expenses
  
  // Last: Independent tables
  'profiles',           // Referenced by audit_logs
];

// Phase 1: Delete in correct order
for (const tableName of orderedTables) {
  await supabase.from(tableName).delete()...;
}

// Phase 2: Insert in same order
for (const tableName of orderedTables) {
  await supabase.from(tableName).insert(tableData.rows);
}
```

## Como Funciona

### 1. Detecção do Tipo de ID

Para cada tabela, o código:
1. Pega o primeiro registro do backup
2. Examina o valor do campo `id`
3. Detecta se é UUID (string com hífens) ou bigint (número)

### 2. Condição Apropriada

**Para tabelas com UUID** (ex: `profiles`):
```typescript
.delete().neq('id', '00000000-0000-0000-0000-000000000000')
```
- Deleta todos os registros onde id ≠ UUID nulo
- Como nenhum registro real tem esse UUID, todos são deletados

**Para tabelas com bigint** (ex: `categories`, `expenses`):
```typescript
.delete().gte('id', 0)
```
- Deleta todos os registros onde id >= 0
- Como todos os IDs válidos são >= 0, todos são deletados

### 3. Fallback para Tabelas Vazias

Se o backup não tem dados para uma tabela:
```typescript
deleteQuery = deleteQuery.gte('id', 0);
```
- Usa condição numérica por padrão
- Falha graciosamente se a tabela já estiver vazia

## Limitações Conhecidas

### Falta de Transação Real
O código atual não usa transações PostgreSQL nativas:
```typescript
// Atual: Delete + Insert sequencial (sem transação)
await supabase.from(tableName).delete()...;
await supabase.from(tableName).insert(tableData.rows);
```

**Risco**: Se o INSERT falhar após o DELETE, os dados são perdidos.

**Solução Futura**: Usar transações PostgreSQL via RPC:
```sql
-- Criar função no PostgreSQL
CREATE OR REPLACE FUNCTION restore_table_data(
  table_name text,
  data jsonb
) RETURNS void AS $$
BEGIN
  -- Tudo dentro de uma transação
  EXECUTE format('DELETE FROM %I WHERE id >= 0 OR id IS NOT NULL', table_name);
  -- INSERT dos dados...
END;
$$ LANGUAGE plpgsql;
```

### Sem Rollback Automático
Se a restauração falhar no meio:
- Algumas tabelas podem estar restauradas
- Outras podem estar vazias
- Não há rollback automático

**Mitigação Atual**:
- Status do restore job é marcado como "failed"
- Mensagem de erro indica qual tabela falhou
- Usuário pode tentar restaurar novamente

## Teste da Correção

Para testar a restauração:

1. **Crie um backup completo**:
   - Acesse a página de backups
   - Clique em "Criar Backup"
   - Escolha "Backup Completo" (inclui profiles + outras tabelas)
   - Aguarde conclusão

2. **Restaure o backup**:
   - Clique em "Restaurar" no backup criado
   - Confirme a operação (⚠️ isso deletará dados atuais!)
   - Aguarde conclusão

3. **Verifique o resultado**:
   - Status do restore job deve ser "completed"
   - Todas as tabelas devem estar restauradas
   - Verifique especialmente:
     - `profiles` (UUID)
     - `categories` (bigint)
     - `expenses` (bigint)
